# 线程池 / 多线程代码调试指南

> 适用场景：业务逻辑被丢进线程池（`ExecutorService` / `FutureTask` / `CompletableFuture`）异步执行，主线程用 `future.get(timeout)` 收结果。断点停不住、结果被丢、线程之间乱跳、异常看不到，都属于这一类问题。

---

## 一、为什么线程池代码难调试

| 痛点 | 原因 |
| --- | --- |
| **断点"卡不住"整个流程** | 主线程 `future.get(timeout)` 有超时。你在 worker 线程断点上停留超过 timeout，主线程直接超时返回、丢弃结果，流程往下走了，人还停在断点上。 |
| **线程之间来回跳** | 多个 worker 线程并发跑同一段 `call()`，IDE 断点默认"挂起全部线程"，一恢复立刻被下一个线程再次命中。 |
| **异常凭空消失** | `Future` 会把 `call()` 里抛出的异常吞进去，只有调用 `get()` 时才抛出；如果 `catch` 里只打了 `debug` 日志，级别没开就什么都看不到。 |
| **上下文丢失** | `ThreadLocal` / MDC(traceId) / 事务 / SecurityContext 不会自动跨线程传递，进了 worker 线程就变 null，行为和主线程不一致。 |
| **短方法难定位** | `call()` 往往只有几行就委托给下游，执行极快，靠"手速"停断点根本来不及。 |

---

## 二、通用调试方法（按性价比排序）

### 方法 1：调试时降级为「同步 / 单线程」执行 ⭐ 最有效

让任务在**当前线程**直接跑，整条链变成线性单线程，断点想停哪停哪，也不受超时影响。

**1a. `FutureTask` 直接 `run()`**

```java
// 异步（原始）
executorService.submit(futureTask);
// 调试：当前线程同步执行，后续 task.get() 立即返回
futureTask.run();
```

**1b. 用「同步执行器」替换线程池**

```java
// 当前线程执行器：谁提交谁执行
Executor directExecutor = Runnable::run;
// Guava 也有现成的：MoreExecutors.directExecutor()
```

**1c. 线程池核心数临时设为 1**

```java
new ThreadPoolExecutor(1, 1, ...);   // 任务串行，跟起来不乱（仍在别的线程，超时仍需处理）
```

> `1a`、`1b` 直接消除了跨线程和超时两个问题，最推荐。

### 方法 2：用「调试开关」控制同步/异步，避免误提交 ⭐ 推荐长期保留

不要手动改代码再改回去（容易漏、容易误提交）。用系统属性 / 环境变量 / Spring Profile 控制：

```java
if (Boolean.getBoolean("project.debug.sync")) {
    futureTask.run();              // -Dproject.debug.sync=true 时单线程
} else {
    executorService.submit(futureTask);
}
```

启动参数加 `-Dproject.debug.sync=true` 即进入单线程调试模式，线上默认异步。本项目已把这个开关封装成 `DebugExecutors`，见第四节。

### 方法 3：放大或去掉 `future.get` 超时

只要还走线程池，就必须处理超时，否则断点停一会儿结果就被丢：

```java
task.get(12, TimeUnit.SECONDS);   // 原始
task.get();                       // 调试：无限等待
task.get(10, TimeUnit.MINUTES);   // 或调大
```

同样建议用开关包起来，别硬改。注意**多层嵌套线程池时以最小的超时为准**（外层先超时，内层白等）。

### 方法 4：仍要多线程调试时的 IDE 技巧（以 IntelliJ IDEA 为例）

- **改断点挂起策略为 Thread**：右键断点 → `Suspend: Thread`，只挂起命中线程，避免所有线程乱跳。
- **条件断点**：右键断点填条件，只停你关心的那条数据 / 那个供应商，例如
  `"ZTRIP".equalsIgnoreCase(item.getHubsCode())`。
- **日志断点（不挂起）**：右键断点 → 取消 `Suspend`，勾选 `Evaluate and log`，填要打印的表达式。适合只想看值、不想中断并发。
- **按线程查看调用栈**：Debug 窗口的 `Threads` / `Frames` 下拉可切换到具体 worker 线程看它的栈。
- **异常断点**：`Run → View Breakpoints → + → Java Exception Breakpoint`，捕获被 `Future` 吞掉的异常（如 `InvocationTargetException`）。

### 方法 5：让异常「现形」

- `Future` 吞异常：确保 `get()` 外层能拿到并打印，或在 `call()` 的 `catch` 里把日志级别从 `debug` 提到 `warn/error`。
- `CompletableFuture` 用 `.whenComplete((r, ex) -> ...)` / `.exceptionally(...)` 打印异常，别只 `thenApply`。
- 临时把日志级别调到 `DEBUG`，别让 `LogUtils.debug` 的错误被静音。

### 方法 6：排查上下文传递问题（ThreadLocal / MDC / 事务）

- worker 线程里 `ThreadLocal`、MDC 的 traceId、`@Transactional` 事务、`SecurityContext` 都**不会自动继承**主线程。
- 用 `TransmittableThreadLocal` + `TtlCallable/TtlRunnable`（阿里 TTL）或包装线程池 `TtlExecutors.getTtlExecutorService(...)` 传递上下文。
- 调试时先确认 worker 线程里这些值是不是 null，很多"诡异 bug"根源在此。

### 方法 7：兜底 —— 绕开线程池写单测直接调 ⭐ 最稳

`call()` 通常只是「组装参数 + 委托下游」。直接对下游业务方法写单元测试 / main，完全不走线程池、不受超时影响，断点最好使：

```java
// 不 new FutureTask、不 submit，直接调 call() 里委托的那个方法
var result = downstreamService.doRealWork(query);
```

### 方法 8：加强可观测性（治本）

- **线程命名**：`namingPattern("Xxx-thread-%d")`，日志里一眼看出是哪个池、哪个线程。
- **traceId 串联**：MDC + TTL 把 traceId 带进 worker 线程，日志能按请求串起来。
- **埋点计时**：任务前后记 `System.currentTimeMillis()`，定位是谁慢、谁超时。

## 三、快速排查清单（Checklist）

- [ ] 断点根本没进来？→ 先确认代码路径真的会执行（`strategy == null`？方法名不匹配？数据被提前过滤？）
- [ ] 停一会流程就跑没了？→ **`future.get(timeout)` 超时**，先放大/去掉超时
- [ ] 线程之间乱跳？→ 断点 `Suspend` 改 **Thread** + 条件断点
- [ ] 想线性跟读？→ **同步执行**（`futureTask.run()` / 单线程池 / 直接执行器）
- [ ] 报错但看不到？→ 异常断点 + 提高 `catch` 日志级别 + `get()` 处打印
- [ ] worker 里取值是 null？→ **上下文没传递**（ThreadLocal/MDC/TTL/事务）
- [ ] 只想验证业务逻辑？→ **绕开线程池写单测**直接调

## 四、本项目的「调试开关」工具类（已落地）

已在 `hotel-providers-adapter-core` 落地工具类 `com.tem.hotel.providers.adapter.manager.DebugExecutors`，统一切换同步/异步与超时，靠 VM 参数控制，线上零影响：

```java
package com.tem.hotel.providers.adapter.manager;

import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.FutureTask;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

public final class DebugExecutors {

    /** -Dproject.debug.sync=true 时任务在当前线程同步执行 */
    public static final boolean SYNC = Boolean.getBoolean("project.debug.sync");

    private DebugExecutors() {
    }

    /** 提交任务：调试模式下当前线程同步执行（get 立即返回），否则进线程池异步执行 */
    public static void dispatch(ExecutorService executor, FutureTask<?> task) {
        if (SYNC) {
            task.run();
        } else {
            executor.execute(task);
        }
    }

    /** 取结果：调试模式下无限等待（避免断点停留导致超时丢结果），否则按传入的超时 */
    public static <T> T get(FutureTask<T> task, long timeout, TimeUnit unit)
            throws InterruptedException, ExecutionException, TimeoutException {
        return SYNC ? task.get() : task.get(timeout, unit);
    }
}
```

调用处：

```java
DebugExecutors.dispatch(executorService, futureTask);
// ...
ResponseDto r = DebugExecutors.get(task, 12, TimeUnit.SECONDS);
```

> 异步分支统一用 `executor.execute(task)`：本项目线程池 `ThreadPoolMonitor` 对 `execute()` 和 `submit()` 都做了 MDC 上下文注入，因此改用 `execute` 不会丢 traceId，行为与原来一致。

## 五、本项目的具体落点（示例）

`HotelListServiceImpl#queryHotelList` 这条链路是**两层线程池嵌套**，下面两处都已接入 `DebugExecutors`，一个参数即可切换单/多线程：

| 层 | 类 / 方法 | 线程池 | 超时 | 说明 |
| --- | --- | --- | --- | --- |
| 第 1 层 | `HotelExecute.execute()` → `StrategyCallable.call()` | `LoadHotelDetailHubsExecutorManager`（32 线程） | `task.get(12, SECONDS)` | 每个供应商一个任务，反射调策略方法 |
| 第 2 层 | `ListPatternAdapter.getHotelList()` → `SearchSupply.call()` | `HotelHubsExecutorManager`（32/64 线程） | `task.get(30, SECONDS)` | 酒店 ID 每 20 个一组并发查供应商 |

- 外层 12s < 内层 30s，**12s 是最紧的卡**，调试时优先放大它。
- `StrategyCallable.call()` 的 `catch` 只有 `LogUtils.debug`，排查异常时记得提高日志级别。
- 相关文件：
  - `hotel-providers-adapter/hotel-providers-adapter-core/.../manager/DebugExecutors.java`（开关工具类）
  - `hotel-providers-service/.../execute/HotelExecute.java`（已接入：两处 `submit` + `get(12s)`）
  - `hotel-providers-adapter/ztrip-hotel-providers-adapter/.../adapter/ListPatternAdapter.java`（已接入：`execute` + `get(30s)`）
  - `hotel-providers-adapter/tojoy-hotel-providers-adapter/.../adapter/ListPatternAdapter.java`（已接入：`execute` + `get(30s)`）

> 上述两层的 `submit`/`execute` 与 `get` 均已接入 `DebugExecutors`。调试时启动加 `-Dproject.debug.sync=true`，两层任务都会在当前线程线性执行、`get` 不再超时，断点想停哪停哪；不加参数则维持原多线程行为，线上零影响。
